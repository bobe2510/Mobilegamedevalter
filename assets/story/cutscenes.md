# 過場方案：CG 靜畫 + 對話

**結論：可行，而且是這個專案的正解。** 理由在最後一節。

- **開場／結局**：全畫面 CG 靜畫（每人約 3 張，長公主的大結局較多）
- **中間劇情**：洛克人式的對話（立繪 + 文字框），不需要補間動畫
- 播放器**一套共用**：開場、中段對話、結局都走同一支程式

---

## ✅ 播放器已經做好了 — 現在只缺圖

| 東西 | 位置 |
|---|---|
| 播放器 | [`js/cutscene.js`](../../js/cutscene.js) |
| 全部台詞 | [`js/story.js`](../../js/story.js) |
| CG 圖片 | `assets/story/cg/<角色>/open-N.jpg`、`end-N.jpg` |

**要補圖的時候，把檔案丟到上表的路徑就好，程式不用改。**
還沒補的位置會顯示一張虛線佔位卡，上面直接寫著缺哪個檔名，
所以可以一張一張補、隨時進遊戲看效果。

### 遊戲裡什麼時候會播

| 時機 | 內容 |
|---|---|
| 選好角色按「開始修行」 | 該角色的**開場**（每個角色只自動播一次） |
| 第 3 關開始時 | **中段對話**（洛克人式：關卡畫面當背景，不需要 CG） |
| 第 9 關（第三隻魔王）過關 | 該角色的**結局** → 記錄破台旗標 → 解鎖下一位角色 |
| 標題畫面 →「故事」 | **重看開場**；破過台的角色還會多一顆**重看結局** |

- 一輪的長度是 `js/game.js` 的 `FINAL_STAGE`（目前 9 = 第三隻魔王），想拉長縮短改這個數字就好
- 解鎖條件已經改成**破前一位的台**（`kg_clear_<角色>`）；舊存檔更新時會把當下的魔王數凍結成既得權益，已解鎖的角色不會被鎖回去

### 操作

點畫面任一處推進（還在逐字就先一次補完），左上角「跳過 ▶▶」直接結束整段。
鍵盤的斬／跳／→ 也可以推進。

### 立繪

第一版用的是各角色現成的 `face.png`（圓形頭像，跟選角卡同一張），
熊貓則直接用遊戲內的跟班 sprite。之後若做了半身立繪或表情差分，
在 `js/game.js` 的 `portraitOf` 換路徑即可，播放器不用動。

| 3 | `knight/open-3.jpg` | 小公主潛逃出來，在花園遇到熊貓娃娃。雖然懷疑是陷阱，但因為太可愛還是聽了牠的請求 ✅ **素材已有**（已就位） |

#### ⚠️ 第 1 張是全作最重要的一張，需要一個「線索」

這張的設計是：玩家此時**還不知道長公主的存在**，看到背影會以為那是小公主
對未來自己的想像。**第二輪才會發現：長公主在這一刻就已經出場了。**

問題是，兩姐妹從背後看幾乎一模一樣——都是金髮、高馬尾、紅緞帶、紅披風。
差別在成熟度與瞳色，而**瞳色從背後看不到**。

所以這張要留一個**看得見的線索**，不然反轉會變成「作者說是就是」，
而不是「玩家自己發現」：

- ✅ **讓大劍入鏡**。長公主用的是大劍，小公主用的是長劍，剪影差很多
- ✅ 身形**明顯更高更成熟**
- ⭕（可選）前景放一把小公主自己的長劍或木劍當對照

有了線索，第二輪玩家會有「原來如此」的快感；沒有線索，只會覺得被騙。

#### ⭕ 可選的回收：長公主篇開場用同一個構圖，但從正面

同樣的地點、同樣的姿勢，這次看得到臉——**紅瞳**。
成本只是多一張圖，但會是很強的呼應。

## 四、CG 規格

| 項目 | 規格 |
|---|---|
| 尺寸 | **1600 × 900**（16:9） |
| 格式 | JPEG，品質 78～85（實測 262～321 KB／張） |
| 文字 | **圖上不要有任何文字**，台詞由程式繪製（方便改字、之後也能多語系） |
| 直向手機 | CG 置中留黑邊，文字框放下方——這是標準做法，不用另外畫直式 |
| 命名 | `assets/story/cg/<角色>/open-N.jpg`、`end-N.jpg` |

### 生成用的 prompt 模板

```
[貼上 assets/PROMPTS.md 的角色設定]

Anime cutscene illustration, official game CG quality, cel shading,
cinematic composition, 16:9 horizontal.

Scene: [這裡寫該張的內容]

No text, no letters, no watermark, no signature, no UI elements.
Leave the bottom third relatively simple — a dialogue box will be drawn there.
```

最後那句很重要：**下方三分之一要留簡單一點**，文字框會蓋在那裡。

## 五、對話系統（洛克人風格）

| 元素 | 規格 |
|---|---|
| 立繪 | 半身，透明 PNG，約 400px 高。可先用現有的 `turnaround/front3q.png` 裁半身 |
| 表情差分 | 每人 2～3 種（普通／激動／哭或怒）。**這是 CP 值最高的一項**，讓對話活起來 |
| 文字框 | ✅ 已實作：程式繪製、逐字顯示、點擊推進、可跳過 |
| 資料格式 | ✅ 已實作：`{ cg, who, name, text, black, center, hold }`，`cg` 有值就換背景圖 |

表情差分不是第一版必要的，但只要每人多三張半身圖，整個對話的質感會差很多。
（第一版先用圓形頭像 `face.png`，換成半身立繪時播放器不用改。）

## 六、技術：載入量不是問題

實測數字：

| 項目 | 大小 |
|---|---|
| 目前**實際首次載入**（程式 + 封面 + 結算插畫 + 一位角色的動作圖） | 約 **1.9 MB** |
| 一張 CG（1600×900 q78） | 約 **250 KB** |
| 預估 CG 總數（3 人 × 開場 3 + 結局 3，長公主加碼） | 約 **21 張 ≈ 5.2 MB** |

**關鍵：CG 要延遲載入。**（✅ 已實作）播到那一幕才抓那張圖，並在對話進行時
預抓後面三句要用的圖。這樣：

- 首次載入維持在 **1.9 MB**，不會因為劇情變多而變慢
- 每個過場只多花 250 KB，在 4G 上約 0.3 秒，用預抓可以完全蓋掉

角色動作圖也已經是「只載入選中的那位」，同樣的原則。

## 七、為什麼這個方案是對的

1. **成本可預期**：靜畫的數量是有限且可數的，不像補間動畫會無限膨脹
2. **AI 生圖最擅長的就是單張構圖**——不需要幀間一致性，是它最穩的區塊
3. **播放器寫一次用到底**：開場、中段、結局、甚至之後的支線都共用同一支
4. **是經典做法**：洛克人、火焰紋章、逆轉裁判全都是這個結構，玩家很熟悉
5. **可以分批上線**：先做小公主的 6 張，其他兩人之後補，不會卡住任何東西

唯一要守的紀律是**下方留白**與**圖上不要有字**，其餘都很自由。
